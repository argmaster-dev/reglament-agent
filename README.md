# Агент поиска ответов по регламентам

Прототип для задачи «Поиск ответов по корпоративным документам» конкурса «ИИкузница», трек «Аналитик данных».

Сотрудник задаёт вопрос в чате. Агент отвечает коротко, своими словами, со ссылками на пункты регламентов. Если ответ зависит от подразделения или этапа, агент уточняет. Если ответа в регламентах нет, агент создаёт обращение в службу качества. Ответ эксперта пополняет базу знаний, и на повторный вопрос агент отвечает уже по нему.

## Состояние

Идёт спринт 26–28 ноября 2026 года. Доступна первичная загрузка и версионирование регламентов.

Профиль сотрудника хранит подразделение, должность или роль в процессе и дату подтверждения.
Подразделение в вопросе действует для текущей темы. Чтобы поменять профиль, можно сказать
«Я теперь в Дирекции ИБ» или «Моя должность — логист». Профиль виден и сбрасывается из чата.
`DIALOG_PROFILE_MAX_AGE_DAYS` задаёт порог повторного подтверждения подразделения. По умолчанию
это 30 дней. Одно подтверждение предлагается за диалог при первом вопросе, где нужен профиль.

## Загрузка регламентов

Понадобятся Python 3.12+, uv, PostgreSQL с расширением pgvector и локальная Ollama с моделью `bge-m3`. Для базы и тестовой почты предусмотрен Compose. При первом запуске создайте пароль базы, сохраните его и при последующих запусках используйте то же значение. При подключении через URL специальные символы пароля требуют percent-encoding.

```bash
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export CHAINLIT_AUTH_SECRET="$(openssl rand -hex 32)"
docker compose up -d --wait postgres mailpit
export DATABASE_URL="postgresql://regulations:${POSTGRES_PASSWORD}@127.0.0.1:${REGULATIONS_DB_PORT:-5432}/regulations"
uv sync --locked
uv run python -m reglament_agent.ingest load docx/
```

Для существующей базы достаточно задать её `DATABASE_URL`. Адрес Ollama по умолчанию — `http://127.0.0.1:11434`, его можно изменить через `MODEL_OLLAMA_URL`. Для сервиса нужны права установки расширения или заранее установленный pgvector. Миграции применяются при запуске загрузки. Векторы вычисляются на CPU.

Команда читает карточки из `docx/documents.toml` и печатает JSON по каждому файлу. При повторе того же файла возвращается номер сохранённой версии. При замене исходник, пункты и переключение активной версии публикуются одной транзакцией. Поиск читает только активные документы и учитывает подразделение и этап.

Тесты запускаются командой `uv run pytest`. По умолчанию они используют временный PostgreSQL из pgserver. Если задан `DATABASE_URL`, тесты создают в этой базе изолированную схему.

## Поиск и источники

Поиск объединяет по позициям три списка кандидатов: близкие векторы, совпадения значимых слов и совпадения фразы. Сокращения раскрываются по глоссарию заказчика. Если подразделение неизвестно, выдача сохраняет места для нескольких подразделений с совпадениями. При известном подразделении или этапе фильтр применяется до ранжирования.

Для маршрута диалога `reglament_agent.storage.retrieve.retrieve` возвращает пункты и отдельный список опубликованных FAQ от подключённого поставщика. Ссылка на пункт хранит номер редакции, номер пункта и, при необходимости, предложение или колонку таблицы. По этой ссылке `reglament_agent.storage.sources.point_view` открывает текст соответствующей редакции.

## Локальный запуск

Для публикации и восстановления стенда после перезагрузки см. [инструкцию финального стенда](deploy/README.md).

Нужны Docker, Ollama с моделями `qwen3.5:9b-q4_K_M` и `bge-m3`, файл `.env` (образец — `.env.example`).

```bash
cp .env.example .env   # заполните пароли и секрет
docker compose up -d --build --wait
docker compose exec -T app python -m reglament_agent.ingest load docx/
```

Вторая команда выполняет первую загрузку регламентов внутри контейнера: Compose передаёт `app` адреса PostgreSQL и Ollama, `docx/` уже лежит в образе, миграции применяются во время загрузки. Повторный демо-прогон идёт на существующей БД без сброса; `make demo-reset` нужен только для явной полной очистки одноразовой БД и требует `DATABASE_URL` в окружении.

Приложение слушает `127.0.0.1:${APP_PORT:-8000}`, Postgres и Mailpit опубликованы только на loopback. Сеть `backend` внутренняя.

**Ollama на хосте.** Контейнер обращается к ней через `host.docker.internal` (`extra_hosts: host-gateway`). Для контейнера задайте `CONTAINER_OLLAMA_URL` с адресом локального Docker-моста, на котором доступна Ollama. Для финального стенда используйте входящий сокет из инструкции выше. Альтернатива — запустить приложение на хосте: `make run` (Chainlit, `src/reglament_agent/chat/app.py`, файл появляется вместе с чатом; читает `.env`, `MODEL_OLLAMA_URL=http://127.0.0.1:11434`).

**Сброс демо.** `make demo-reset` стирает всю схему БД, применяет миграции и загружает все регламенты; `make demo-reset-without-td` — без `td-project` (чтобы показать добавление регламента). Команда требует `--yes` или `DEMO_RESET_ALLOWED=1`. Переменные: `EMBEDDER=ollama|fake`, `DEMO_RESET_SCHEMA` (по умолчанию `public`). Выводит JSON: документы, пункты, секунды.

**Проверка состояния.** `GET /health` (роутер `reglament_agent.ops.health.router`, подключается в приложение) возвращает JSON по БД, Ollama и SMTP; 503 при недоступности любой из этих зависимостей.

## Ответ эксперта по почте

Основной путь ответа службы качества — почта, кабинет остаётся для просмотра, правки и снятия записи.
Агент отправляет письмо об обращении службе качества с сотрудником в копии; эксперт отвечает обычным
«ответить всем». Служба `python -m reglament_agent.quality` раз в `MAIL_REPLY_INTERVAL` секунд читает
ящик службы качества и для каждого нового письма:

1. находит обращение: по `In-Reply-To`/`References` (наш `Message-ID`), иначе по номеру обращения в теме;
   письма без обращения и наши собственные письма пропускаются;
2. письмо самого сотрудника ответом не считается; при заданном `MAIL_QUALITY_ADDRESSES` отвечать могут
   только эти адреса, иначе любой отправитель, кроме сотрудника (отправитель записывается);
3. берёт слова эксперта: без цитаты исходного письма («… пишет:», `> `, «От:»-блока, Original Message),
   без подписи (`-- `, «Отправлено с iPhone»); предпочитается text/plain, иначе HTML переводится в текст;
4. отвечает так же, как кабинет: сотрудник видит ответ в своём диалоге, ответ публикуется в FAQ
   («вне регламентов», с привязкой к подразделению обращения). Повторный ответ эксперта заменяет прежний
   и запись FAQ (дублей нет); снятая в кабинете запись остаётся снятой;
5. запоминает `Message-ID` в `mail_replies`, повторная доставка письма ничего не меняет.

Настройка (переменные окружения):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MAIL_REPLY_ENABLED` | `false` | включить опрос ящика в службе качества |
| `MAIL_REPLY_SOURCE` | `mailpit` | `mailpit` (стенд) или `imap` (продукт) |
| `MAIL_MAILPIT_URL` | `http://localhost:8025` | адрес HTTP API Mailpit (в compose: `http://mailpit:8025`) |
| `MAIL_REPLY_INTERVAL` | `15` | пауза между опросами, с |
| `MAIL_QUALITY_ADDRESSES` | пусто | список адресов службы качества через запятую |
| `MAIL_IMAP_HOST`, `_PORT`, `_USER`, `_PASSWORD`, `_FOLDER` | | параметры IMAP (SSL) |

Для публикации в FAQ нужен тот же `EMBEDDER`, что и у кабинета. Один проход вручную (демонстрация):
`DATABASE_URL=... MAIL_REPLY_ENABLED=true python -m reglament_agent.quality poll-replies`.

На демонстрационном стенде ящик службы качества — Mailpit. В веб-интерфейсе Mailpit нет кнопки «ответить»,
поэтому эксперт отвечает из любого почтового клиента, настроенного на SMTP Mailpit (порт 1025, без
авторизации): «ответить всем» на письмо «[Обращение №…]» (клиент сам добавит `In-Reply-To` и «Re:» в тему).
Ответ появится в Mailpit, и при следующем опросе агент опубликует его.

## Конфигурация под GPU заказчика

Параллельные генерации задаются `MODEL_CHAT_SLOTS` (целое ≥ 1, по умолчанию 1; в `compose.yaml` пробрасывается в `app`). Лишние запросы встают в FIFO-очередь с показом позиции. Длину очереди ограничивает `MODEL_GENERATION_MAX_WAITERS` (по умолчанию 3) на каждый слот: при N слотах в очереди помещается N × это значение (при N=1 ровно столько же, сколько раньше). При переполнении выбрасывается `GenerationQueueFull`, чат отвечает «стенд занят». Эмбеддинги идут мимо слотов генерации; `MODEL_EMBED_NUM_GPU` (по умолчанию 0 = CPU) переводит их на GPU. На стороне сервера Ollama `OLLAMA_NUM_PARALLEL` должен быть не меньше `MODEL_CHAT_SLOTS`, иначе запросы выстроятся внутри Ollama.

Пример для GPU с большой памятью, 128 ГБ (значения примерные, не измерены):

```bash
MODEL_CHAT_SLOTS=4
MODEL_GENERATION_MAX_WAITERS=4   # очередь до 16 ожидающих
CHAT_MAX_IN_FLIGHT=20            # не меньше 4 + 16, иначе пятый запрос получит «стенд занят» до очереди модели
MODEL_EMBED_NUM_GPU=99
OLLAMA_NUM_PARALLEL=4   # переменная сервера Ollama, не приложения
```

`CHAT_MAX_IN_FLIGHT` ограничивает общее число одновременных ходов чата, включая поиск, поэтому его нужно держать не меньше `MODEL_CHAT_SLOTS` × (1 + `MODEL_GENERATION_MAX_WAITERS`), иначе лишний запрос получит «стенд занят» раньше, чем попадёт в очередь модели.

Состояние слотов: `OllamaClient.slot_status()` возвращает `{slots, busy, waiting, max_waiting}`; тот же блок отдаёт `GET /health` в поле `generation` (только очередь чата; клиент индексации со своим слотом в него не входит). В журнале вызовов (`CallRecord`) у каждого chat-вызова есть `slots`, `busy` (занято слотов на момент старта, включая этот вызов), `waiting` (сколько уже ждало к его приходу) и `queue_ms`.

## Запуск (разработка)

```bash
export PATH=$HOME/.local/bin:$PATH
uv sync
uv run chainlit run src/reglament_agent/chat/app.py --headless --port 8000
```

Откройте http://localhost:8000 и выберите роль. При настроенной `DATABASE_URL` чат ищет по активным версиям регламентов и опубликованным ответам службы качества. Кнопка под ответом открывает точное предложение или колонку. При нехватке основания обращение и письмо попадают в очередь одной транзакцией. Для локального предпросмотра интерфейса без БД используются заглушки.

| Переменная | Назначение |
|---|---|
| `CHAT_EXPERT_PASSWORD` | пароль роли «Служба качества». Если он пуст или не задан, вход эксперта отключён |
| `CHAINLIT_AUTH_SECRET` | секрет подписи сессий; если не задан, создаётся случайный на время процесса |
| `CHAT_TRUSTED_HEADER` | например `X-User-Email`: личность берётся только из этого заголовка. Прокси обязан сам выставлять его и удалять из запросов клиента |
| `CHAT_EXPERT_EMAILS` | список адресов экспертов через запятую (только в режиме доверенного заголовка) |
| `CHAT_SERVICES_FACTORY` | Фабрика сервисов чата. В Compose по умолчанию используется `reglament_agent.dialog.services:build_services` |
